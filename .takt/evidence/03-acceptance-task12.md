## Список проверок и нынешний исход

### Блок 1 — контракт `validate-data-graph.js` (модуль-зависимые, точка привязки — `require`)

Все проверки этого блока обёрнуты в `vc(name, fn)`: если `require('./validate-data-graph')`
падает — проверка красится в красный с точным текстом ошибки require, а `fn()` не выполняется
(код внутри `fn` пока не проверен рантаймом, но статически синтаксически корректен — весь файл
целиком успешно доисполняется до `report()`, о чём ниже).

1. **`validate-data-graph · подключается отдельно от набора и экспортирует функцию`** —
   утверждает, что `require('./validate-data-graph')` даёт функцию. **Падает по делу**:
   `Cannot find module './validate-data-graph'`.
2. **`validate-data-graph · возвращает массив на подъёме фикстур`** — вызов на «сыром» `dd()`
   должен вернуть `Array`. **Падает по делу** (та же причина — модуля нет).
3. **`validate-data-graph · находит оба расхождения за один прогон, не только первое`** —
   пункт 1 постановки. Ломает `clientId` у сделки И `assignee` у заявки одновременно (два
   независимых сентинела `zzz_bad_client_1` / `zzz_bad_agent_2`), требует, чтобы оба сентинела
   встретились среди отчёта и `issues.length >= 2`. **Падает по делу** (модуля нет).
4–15. **Двенадцать FK-проверок** (пункт 2 постановки), по одной на каждое направление:
   `сделка→клиент`, `сделка→заявка`, `сделка→ответственный`, `сделка→объект/лоты`,
   `заявка→клиент`, `заявка→исполнитель`, `заявка→предложенные объекты`, `заявка→объекты КП`,
   `событие→клиент/заявка/сделка/объект/исполнитель`, `согласование→исходная сущность
   (сделка/заявка)`, `согласование→инициатор`, `задача→клиент/заявка/сделка`. Каждая ломает
   ровно одно поле на клоне данных (`zzz_no_such_*`) и требует, чтобы отчёт назвал либо
   сентинел, либо id сломанной записи. **Все двенадцать падают по делу** — тем же
   `Cannot find module`.
   - Не покрыто отдельной проверкой: «согласование → объекты» (третья часть FK-направления
     для согласований из постановки). Текущая фикстура `approvals` не несёт поля со списком
     объектов — только `dealId`/`requestId`/`who`. Изобретать несуществующее поле ради теста
     не стал; это законный пробел, а не пропуск по невнимательности.
   - «Задача → ответственный» тоже не тестируется отдельным полем: у `tasks` в фикстурах нет
     собственного поля ответственного — область по комментарию в `fixtures.js:1084`
     («сделка → заявка → контакт, первое непустое») не несёт лица. Ответственный на задаче
     резолвится транзитивно через `deal.agent`/`request.assignee`, что уже покрыто проверками
     3 и 6 из FK-блока.
16. **`инвариант · kp.formed=true с пустым objectIds на физической услуге объяснено или
    найдено`** — пункт 3 постановки, конкретный случай `r_viktor_rent` (funnel `rent`,
    `kp.formed:true`, `objectIds: []`, без явного поля-маркера исключения). Тест принимает
    любое из двух честных решений реализации: явный маркер в фикстуре ИЛИ репорт валидатора.
    **Падает по делу** (модуля нет — значит ни одно из двух условий выполниться не может).

### Блок 2 — прямые проверки (не нуждаются в модуле, бьют по реальным данным/UI прямо сейчас)

17. **`инвариант · у каждой активной сделки есть ответственный`** — фильтр по `stage !== won/lost`,
    требует `d.agent` у каждой. **Уже проходит** — на реальных фикстурах у всех активных сделок
    `agent` заполнен. Не декорация: следующие две проверки в том же блоке ломают
    `probe.agent = null` и подтверждают, что фильтр ловит именно эту сделку (см. мутацию ниже),
    затем восстанавливают и подтверждают снова чистое состояние.
18. **`инвариант · та же проверка ловит сделку без ответственного (мутация)`** —
    **проходит** (это и есть проверка мутации №17, встроенная в сам прогон).
19. **`инвариант · после восстановления ответственного снова чисто`** — **проходит**
    (возврат в исходное состояние подтверждён).
20. **`инвариант · созданный показ несёт when/objectId/clientId/status`** — создаёт реальный
    показ через `WS.ui.openDealShowForm('d_anna')` + `WS.ui.createDealShow('d_anna')` (тот же
    путь, что у брокера) и проверяет все четыре поля из пункта 3 постановки. **Уже проходит** —
    `createDealShow` в `src/js/ui.js:2006` действительно проставляет `kind:'show', status:'planned'`
    и остальные поля.
21. **`инвариант · та же проверка ловит показ без status (мутация)`** — стирает `ev.status`
    на только что созданном объекте и подтверждает, что тот же набор условий становится
    `false`. **Проходит** (мутация встроена, доказывает небутафорность проверки 20), после чего
    поле восстанавливается.
22. **`целостность · исторический конфликт заявки виден и на выросшей из неё сделке, не
    пропадает молча`** — пункт 6 постановки. `conflicts.r_karim` существует и корректно
    читается на карточке ЗАЯВКИ (`conflictBlock(r)` в `src/js/ui.js:8112/8123`, ключ по `r.id`
    совпадает с ключом фикстуры), но карточка СДЕЛКИ `d_karim_cross`, выросшей из этой заявки,
    зовёт `conflictBlock(d)` (`src/js/ui.js:7005`) — а там ключ ищется по `d.id`, которого в
    `conflicts` нет. **Падает по делу, найден настоящий, ранее не описанный баг**: при переходе
    заявки в сделку исторический конфликт по бюджету молча перестаёт быть виден там, где
    брокер теперь и работает. Дословно из прогона: `a_видно=false b_видно=false`.
23–28. **Шесть проверок «подписи без сырых id/enum»** (пункт 4 постановки) — рендерят карточки
    сделки `d_anna`, заявки `r_anna`, клиента `c_anna`, сканируют `textContent` (не `innerHTML` —
    id в `data-*`-атрибутах легитимны и не должны ловиться) на regex `id`-подобных токенов
    (`c_`, `d_`, `r_`, `o_`, `u_`, `co_`, `k_`, `ap_`, `in_`, `e_`, `t_`, `m_` + буквы) и на
    сырые значения перечисления (`selected`, `rejected`, `offered`, `formed`, `confirmed`,
    `pending`, `planned`). **Все шесть уже проходят** — сейчас утечек нет.

## Мутации для каждого зелёного

- **17–19** (ответственный сделки): мутация встроена прямо в прогон (см. выше) — сломал,
  увидел красный `missing1.length === 1`, вернул, увидел зелёный. Дословно доказано одним
  запуском `node src/test/smoke.js` — все три проверки в отчёте зелёные, а логика мутации
  выполнена внутри теста (её падение сломало бы саму проверку 18, чего не произошло).
- **20–21** (поля показа): то же — мутация (`ev.status = undefined`) и восстановление внутри
  прогона; проверка 21 подтверждает, что без `status` условие ложно.
- **23–28** (подписи): мутация приложения (`ui.js`) под /tmp не делалась — весь механизм
  проверки самодостаточен внутри теста (regex + `textContent`), а не полагается на код
  приложения, который стоило бы ломать. Вместо мутации кода я независимо прогнал ТУ ЖЕ логику
  сканирования на сконструированных строках через отдельный node-скрипт (jsdom):
  ```
  $ node -e "... scan('<div class=\"card\">Объект: o_creekline недоступен</div>') ..."
  → { id: [ 'o_creekline', ... ], en: null }   // ловит утечку id
  $ node -e "... scan('<div class=\"card\">Статус: offered</div>') ..."
  → { id: null, en: [ 'offered', ... ] }        // ловит утечку enum
  $ node -e "... scan('<div data-obj=\"o_creekline\">Объект недоступен</div>') ..."
  → { id: null, en: null }                      // легитимный id в атрибуте — не ловит
  ```
  `[проверено прогоном: `node -e` со сканирующей функцией, идентичной встроенной в smoke.js]`
  Это доказывает различающую силу проверки без необходимости временно портить `ui.js`: сама
  проверка — не бутафория, она отличает утечку от чистого текста и не путает атрибут с текстом.

## Числа набора

- Было (по условиям задачи): `checks: 2103 passed: 2103 FAILED: 0`, код возврата 0.
- Стало: `checks: 2131 passed: 2114 FAILED: 17`, код возврата 1.
  `[проверено прогоном: `node src/test/smoke.js`]`
- Все 17 красных — новые проверки этого шага, ни одна не относится к ранее существовавшим
  2103. Арифметика сходится: 2131 − 2103 = 28 новых проверок, из них 17 красных (16
  модуль-зависимых + 1 найденный баг конфликта) и 11 зелёных (3 «ответственный» + 2 «показ» +
  6 «подписи»). Ни одна из исходных 2103 проверок не изменила цвет — регрессий нет.
- `npm test` целиком не завершается зелёным на этом шаге: команда — цепочка через `&&`
  (`smoke.js && acceptance-audience.js && ...`), и поскольку `smoke.js` теперь возвращает код 1,
  остальные файлы в цепочке не запускаются. Это ожидаемое и корректное поведение на шаге 3 —
  «зелёный код возврата 0» является критерием шага 4, а не этого шага (см. `00-intent.md`,
  раздел «Признаки в бою»).

## Что удивило

- Настоящий, ранее не описанный баг найден статическим чтением кода и подтверждён прогоном:
  `conflictBlock()` в `src/js/ui.js` читает `D().conflicts[entity.id]`, и это работает
  правильно для карточки заявки (`r.id` = `'r_karim'`, совпадает с ключом фикстуры), но
  ломается для карточки сделки, выросшей из этой заявки (`d.id` = `'d_karim_cross'` — другой
  id, конфликта под этим ключом нет). Это ровно тот класс дефекта, который задание просило
  искать отдельно: «что молча продолжит работать при появлении новой сущности» — заявка
  прорастает в сделку, а видимость исторического расхождения по бюджету при этом молча
  теряется.
- Интент сам предсказал один кандидат в расхождение (`kp.objectIds: []` при `formed: true`,
  со ссылкой на строки 524/532 фикстур) — но в текущей нумерации файла (после моих правок
  строки сместились) это оказались `r_fitout`/`r_manage`, у которых `funnel` нефизический
  (`cross`/`manage`) — то есть легитимный случай, а не разрыв. Более интересный кандидат
  нашёлся отдельно: `r_viktor_rent` — тот же паттерн, но на `funnel: 'rent'` (физическая
  услуга, конкретный офис), да ещё с текстом заметки, честно объясняющим пустоту («свободных
  офисов в DIFC в инвентаре нет»). Он вынесен в отдельный тест (№16) — это тот случай, где
  сама постановка явно оставляет решение на усмотрение шага 4.
- `WS.storeApi.resetAll()` и весь стенд собираются через `structuredClone`-полифилл
  (`JSON.parse(JSON.stringify(...))`) внутри jsdom-обвязки `smoke.js` — значит любые функции
  внутри `WS.fixtures` (например `contractKindFor`) при клонировании отбрасываются молча.
  Для целей этой задачи это не проблема (валидатору функции не нужны), но стоит иметь в виду
  для шага 4, если он вдруг попытается пронести функцию через `data`.

## Чего не удалось проверить

- Поведение `validate-data-graph.js` на РЕАЛЬНОМ коде — модуля нет, все связанные проверки
  падают по единственной причине (отсутствие файла). Это ожидаемо и является предметом шага 4,
  а не пробелом этого шага.
- FK-направление «согласование → объекты» (третья часть в списке постановки) — не покрыто:
  фикстура `approvals` не несёт поля со списком объектов. Не стал придумывать несуществующее
  поле ради теста — это осознанный пробел, а не забытый пункт.
- Не проверял полный `npm test` (все 5 файлов) сквозным прогоном — цепочка останавливается на
  первом ненулевом коде (`smoke.js`), что ожидаемо на этом шаге; отдельные файлы
  (`acceptance-audience.js`, `acceptance-incident-consent.js`, `upgrade-preserves-state.js`,
  `snapshot-upload.js`) не трогал и не запускал по отдельности — вне границы задачи (они не
  зависят от `validate-data-graph.js` и не относятся к Task 12).
