# Шаг 0 — Намерение и граница (Task 12)

Второй прогон эксперимента о конструкции такта. Класс `local`, состав узлов
0 · 3 · 4 · 5 · 7 · 9 · 10 · 12 · 13 — тот же, что на Task 8.

Природа задачи третья, и это в замысле эксперимента: Task 7 был машиной состояний,
Task 8 — именование и понятность подписей, здесь — **данные и корректность**.

## Что делаем

Стенд живёт на наборе фикстур: сделки ссылаются на клиентов, заявки — на объекты,
согласования — на основания. Сегодня ни одна из этих связей не проверяется ничем:
битая ссылка обнаруживается тем, что экран рисует пустоту, и только если на этот
экран кто-то зайдёт.

Заводим проверку целостности данных, которая гоняется в наборе и падает на разрыве.

## Пункты постановки — по каждому шаг 12 обязан ответить отдельно

1. **Проверка возвращает все ошибки за один прогон**, а не останавливается на первой.
2. **Внешние ключи** проверяются по пяти направлениям: сделка → клиент, заявка,
   ответственный, объект/лоты · заявка → клиент, исполнитель, предложенные объекты,
   объекты коммерческого предложения · событие → клиент, заявка, сделка, объект,
   исполнитель · согласование → исходная сущность, инициатор, объекты ·
   задача → клиент / заявка / сделка / ответственный.
3. **Рабочие инварианты** проверяются: у активной сделки есть ответственный ·
   `kp.formed === true` имеет непустой набор документов либо явно допустимый пустой
   набор для нефизической услуги · согласование в ожидании ссылается на актуальную
   версию основания · показ имеет `when`, `objectId`, `clientId`, `status` ·
   производные счётчики не дублируются константами в фикстурах и интерфейсе.
4. **Пользовательские подписи не содержат внутренних служебных слов** — значений
   перечислений, кодов статусов и идентификаторов.
5. **Проверка запускается после подъёма фикстур** и после каждого приёмочного сценария,
   а не одним разовым вызовом.
6. **Найденные расхождения исправлены**, причём осмысленные исторические конфликты не
   удаляются: они помечаются датой или версией, и проверяется, что интерфейс не выдаёт
   историю за текущий факт.

## Расхождение плана с репозиторием — то же, что на Task 8

План (`wewall/docs/wespace/plans/2026-09-02-wespace-stand-fix-plan.md`, раздел Task 12)
называет файл `src/test/acceptance-broker-flows.js` и команду `npm run test:broker`.
**Ни того, ни другого в репозитории нет.**

```
$ for f in src/js/fixtures.js src/js/store.js src/test/smoke.js src/test/acceptance-broker-flows.js; do ...
  ЕСТЬ   src/js/fixtures.js  (1407 строк)
  ЕСТЬ   src/js/store.js  (879 строк)
  ЕСТЬ   src/test/smoke.js  (10157 строк)
  НЕТ    src/test/acceptance-broker-flows.js
  test:broker: НЕТ ТАКОЙ КОМАНДЫ
```
`[проверено прогоном: `ls` по путям плана и чтение `scripts` из `package.json`]`

Решение постановки: приёмочные проверки идут в `src/test/smoke.js`, сама проверка
целостности — отдельным модулем `src/test/validate-data-graph.js`, который smoke
подключает. Команда прогона — `npm test`, как и на Task 8.

**Это повторное расхождение, а не случайность.** План писался 2 сентября и с тех пор
разошёлся с деревом дважды в одном и том же месте. Для эксперимента это наблюдение об
узле 0: он окупается ровно тем, что сверяет план с репозиторием до того, как реализация
начнёт писать код по несуществующим путям.

## Чего в этой задаче не делаем

Проверку в продукте (`src/js/`) не заводим — она только для тестов. Валидатор, который
гоняется у пользователя, это другая задача с другой ценой: он требует решения, что делать
при найденном разрыве в бою, а такого решения нет.

Исторические конфликты в фикстурах не вычищаем, если они осмысленные: в стенде есть
данные, намеренно показывающие прошлое состояние сделки.

## Признаки в бою

```
npm test ⇒ код возврата 0, проверка целостности выполнена и не нашла разрывов
node -e "require('./src/test/validate-data-graph.js')" ⇒ модуль подключается отдельно от набора
```

## Известное заранее

В фикстурах уже видны кандидаты в расхождения: у части заявок стоит
`kp: { formed: true, ..., objectIds: [] }` — сформированное коммерческое предложение с
пустым набором объектов. Это ровно инвариант из пункта 3. Является ли пустой набор
допустимым (нефизическая услуга) или это разрыв — решает реализация, предъявив данные.
